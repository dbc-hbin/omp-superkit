# Performance comparison

Use this when asked to produce a measurement or support a performance decision. For a read-only audit of an existing benchmark or eval claim, use [eval-integrity](../../eval-integrity/SKILL.md) instead. Measuring does not authorize optimization edits, paid runs, or changes to shared systems.

1. **Fix the comparison before timing.** State the decision, metric and unit, the smallest change that would matter, and what completed, correct work looks like. Use the smallest realistic workload that exercises the user's path. Record input identity, size, concurrency and starting state; use the same harness, measurement boundaries, machine, runtime, build settings and cache policy unless one is the variable under test. Give both implementations equivalent production-relevant settings. If those settings cannot be made comparable, limit the claim to the observed configurations rather than choosing an implementation from that result.
2. **Prove what the timer counted.** Read the harness. For each arm, record attempted and successfully completed work, failures, retries, timeouts and skipped work. Check the actual outputs or downstream effects against the same acceptance criteria. Confirm the intended work finishes inside the timed region: await it, consume lazy results and check state when appropriate. A faster result that silently drops rows, serves a different cache path or returns early is not a speedup for equivalent work. Report failed or invalid runs and why; do not trim them away or count failures as useful throughput.
3. **Separate the effect from noise and measurement overhead.** Sample each arm repeatedly for a comparison, with matched warmup or reset and interleaved order when drift is plausible. Record run count and spread as well as a representative result (for example, median and range). Check load and counters for the bottleneck, including the harness or load generator; use a separate profiling run if instrumentation changes the timing. Sanity-check the gain against resource limits and the changed code's share of the work. Scope a microbenchmark to its measured path unless an end-to-end check supports the broader claim. A requested spot estimate can be one labeled sample with work and error checks, not evidence of a winner.

For an authorized iterative optimization, retain a baseline and a fixed harness that reports work and error counts. Measure one change at a time; only keep a change on performance grounds if it beats noise without breaking the existing behavior checks. Stop at the requested decision, target or run limit.

Report **faster**, **slower**, **no measurable difference** (valid comparison but effect within variation), or **inconclusive** (for example, unequal successful work, an untuned arm for an adoption decision, or an unestablished limiter that could change the claim). Include exact inputs and conditions, work/error counts, values with units and spread, observed limiter or what is still unknown, and invocation or evidence pointers. Equal request counts with fewer valid results on one side are unequal work: report the discrepancy, not a speedup.
