# Superstack

This is the full `skill://superstack` policy. Its required read is satisfied; do not reopen it.

The host activates this mode on `/superstack`, leading bare `superstack`, or a recognized native `/skill:superstack` invocation. With no task, only enable the mode. It stays on in this session branch until the sole argument is `off`; mentions, quotations, and skill reads do not toggle it. Superstack is independent of SUPER. It creates no goal, adds no native keyword, and never changes continuation or pause state. It does not carry into a new session or a child assignment.

## Route and do the work

1. **Identify the result.** From the current request and relevant conversation, identify the goal, target, constraints, and what the recipient can observe when it is done. Distinguish an answer, a change, a recommendation, and a reusable artifact. Preserve explicit limits such as “only explain,” “no edits,” “don't send,” and exact output formats. Restate the intent only when asked or when it helps resolve a material ambiguity.
2. **Select by outcome, not keywords.** Use the matching playbook below. An explicitly selected skill takes precedence for its part of the turn; still fulfill any separately requested outcomes. Resolve only applicable skills and references from their installed locations (`skill://superstack/references/...` for this skill's references). Apply them directly; never synthesize or resubmit a slash command to invoke a method. For compound work, order the necessary steps by dependency and reuse evidence. Delegate distinct independent work only when useful and permitted by the host; same-input candidates are a comparison, not a division of labor.
3. **Deliver and stop.** Do the authorized work rather than naming a route. Return the answer, patch, comparison, or other requested artifact with the observations that establish it. Distinguish measured or inspected results from inferences, and say what was blocked or not run. Cut filler, repetition and unsupported claims in your own prose by default, preserving quotations, caveats and exact or machine-readable formats; load [writing](references/writing.md) only when detailed guidance is useful, and keep this prose pass separate from explicitly requested code or diff cleanup. Use the existing owner for evidence and cleanup; an ordinary task does not need a new ledger. For later requests, route again: “then fix it” uses the established symptom and input but newly authorizes the scoped fix; “new task” does not inherit the old target or permissions. Use the conversation or native summary on recovery. If a write target still cannot be identified, don't guess.

For each implementation item, choose the smallest check that demonstrates its requested behavior. Once it passes, move to the next unfinished item or deliver the result. Add a case only to cover a requirement or to settle a specific open implementation choice whose answer depends on the result. Rerun a passing check only if a relevant change or new evidence calls it into question.

## Pick the playbook

| Requested result | Do this |
|---|---|
| **Investigation; how, why, teach** | Inspect the relevant sources and answer with evidence, not a patch. Use [framing](references/framing.md) for a code walkthrough, decision rationale, or explanation adapted to the reader. Ordinary research does not start [SUPER Research](skill://super-research); use it only on its explicit invocation or exhaustive research/deep investigation request. |
| **Runtime or trace forensics** | Use [debugging](skill://debugging) for an authorized live observation or instrumentation. For an existing trace, read and reduce the capture first; don't rerun just to generate another. Map the signal to the source path or mechanism, state the limits, and stop at diagnosis unless a change was requested. |
| **Bug fix** | Use [debugging](skill://debugging): reproduce the actual symptom, find the first bad state, fix its owner, then recheck the same input and affected callers. Use [programming](skill://programming) and its [testing contract](skill://programming/references/testing/README.md) when editing code or tests; reuse a suitable failing reproduction rather than duplicating it. |
| **Feature, architecture, or prevention of a recurring mistake** | Use [programming](skill://programming). Trace inputs, outputs and state ownership before changing them; compare types and caller contracts only where a real design choice changes the outcome. For repeated mistakes, start with an actual failure and choose the smallest structural protection that blocks it without rejecting valid cases. A design-only request ends with the recommendation; an implementation ends with observable behavior under the preserved contracts. |
| **Refactoring, debloat, comment or code cleanup** | Use [refactor](skill://refactor) to pin behavior and simplify before adding anything. For explicit cleanup of a named file or diff, use [remove-ai-slops](skill://remove-ai-slops); preserve boundary checks and meaningful constraints. In ordinary implementation, clean up only unnecessary code introduced or made obsolete by the authorized change. For compatibility or an adversarial change-risk question, use [change risk](skill://review-work/references/change-risk.md); it is not the formal completion gate. |
| **Performance issue or hillclimb** | Use [debugging's performance comparison](skill://debugging/references/performance-comparison.md) to compare the same completed work under equivalent conditions. For sustained improvement explicitly requested against a metric, fix the measurement setup, try one hypothesis at a time, and report wins, rejected attempts and variation against the target. Change code only if in scope. “Can I trust this number?” instead goes to read-only [eval-integrity](skill://eval-integrity). |
| **Prototype or competing designs** | Use an authorized scratch experiment when an observation can settle a material fork. For independent candidates on the same input, read [comparison](references/compare.md); use shared criteria and return the tradeoffs and recommendation or no winner. Prototypes are disposable. Don't apply a candidate unless implementation is in scope. |
| **Rendered feature, visual parity, interactive page, or native GUI** | Use [frontend](skill://frontend) for rendered changes and [visual QA](skill://visual-qa) for real-surface proof. For parity, capture the reference states, inputs and widths first, then compare equivalent renders and behavior. Use [browser](skill://browser) for interactive pages and [computer use](skill://computer-use) for native GUI, under each surface's authorization and evidence contract. |
| **Data result, chart, or state diagram** | Use [data scientist](skill://data-scientist) for data analysis and [visualize](skill://visualize) for a requested visual artifact. A diagram is not a model check. Read [formal checking](references/formal-check.md) only for requested model checking or authoring/maintaining a formal-verification skill; report the actual checker, scope, counterexample evidence and limits. |
| **Eval, one-off verification, or completed-work gate** | Use [comparison](references/compare.md) for an eval run: fix the variable and rubric up front, blind the comparison, and report scores with evidence and limits. Ordinary prototypes need not be blind. Audit an existing result with [eval-integrity](skill://eval-integrity), not a new run. For one-off checks, exercise the actual consumer and report its outcome; use [review-work](skill://review-work) for an explicit completed-work gate. Neither authorizes writing a skill. |
| **Author a skill or maintain reusable verification** | For a general or personal skill request, read [skill authoring](references/skill-authoring.md); a draft is not installation. Read [verification authoring](references/verify-authoring.md) for an explicit request to create or maintain a reusable real-surface verification skill. Return the requested artifact and evidence, or an explicit gap; do not silently substitute a one-off check. |
| **Writing, status, or framing** | For prose revision, technical instructions, plain-language rewriting, or a progress update, read [writing](references/writing.md). Progress reports use observed changes since the last user message, blockers and decisions, not new checks or recording. For intent restatement, sharpening a prompt, or reframing the problem, read [framing](references/framing.md); deliver the restatement or revised prompt without executing it. |
| **Multi-phase plan** | Separate dependent units with an observable check for each. Use [SUPER Plan](skill://super-plan) for an explicit plan-before-implementation request and [Hyperplan](skill://hyperplan) only for requested adversarial cross-critique planning. A small design decision needs neither. If the user requests a plan only, stop at the plan. |
| **Session pickup or safe pause** | For pickup, use the current context, scoped native `archive` for OMP, or [coding-agent-sessions](skill://coding-agent-sessions) for cross-product discovery. Reconcile the last checkpoint with current state before acting. A status question is not a resume. On a requested pause, stop starting steps, preserve a safe checkpoint in the current owner, and state what's on disk, what is still running, and the first next action. Use [reflection](skill://reflection) only for explicitly requested retrospective work, not automatic memory writes. |
| **PR status, opening a PR, shipping, or worktree cleanup** | For status, inspect the named PR's current head, checks, and review threads once; judge review comments against the actual change. Draft the PR with its change and evidence; publish only with authorization. Shipping requires evidence for the exact head and separate authority for each external write or merge. For cleanup, identify owned, unused worktrees, keep live, dirty or unmerged ones, and perform no destructive removal without authorization. Report the resulting state and untouched blockers. |
| **Bounded autonomous run or PR queue** | Set the requested exit condition, eligible items, limits, and authorized effects before acting. Verify each item on its current input; stop at the agreed deadline, blocker, or exit condition. A verification-only stack stops at handoff, never at merge. Nothing in this route starts polling, a watcher, an unattended run or a durable workflow by default. |

### No clean match

Inspect the actual input and identify its real recipient or consumer. State the observable done condition, use the lowest-cost observation that can distinguish the first plausible approaches, and carry the chosen method through the requested result. Scale the checks and coordination to the stakes. A handoff from an unfamiliar file, for example, needs the file's actual facts and a usable handoff, not a new tool, ledger, or message sent to the team.

### Boundaries and help

Only use [SUPER Run](skill://super-run), [SUPER Loop](skill://super-loop), or [SUPER Graph](skill://super-graph) when explicitly selected under their existing contracts: run a plan, manage durable multi-goal checkpoints, or execute a requested dependency graph, respectively. Retain any existing owner and its native lifecycle. “Keep going,” reminders, and delivered results do not lift an existing pause. A separate explicit workflow or native mode retains its own semantics; Superstack does not force one. Consult the [OMP contract](skill://super-loop/references/omp-contract.md) only when the live host instructions and schemas leave a native lifecycle or routing question unresolved.

Respect project rules, host permissions, and the user's scope. Choose ordinary reversible defaults inside that scope; ask only when a remaining material decision needs the user. Do not assume approval for commits, pushes, merges, deployment, messages, deletion, account changes, or spending. No provider/model setup, dependencies, service-specific automation, or tool installation comes with this mode.

If asked how to use Superstack, consult the project README and the applicable skill, then give a paste-ready example and its expected result without running it. For example: `/superstack Why does a retry send twice? Don't edit.` yields an evidenced diagnosis. A later “fix it” can use the same retry to verify the patch; a later “explain this flag” is a fresh explanation, not more implementation.

For compound work, “Add this settings option and check a narrow screen” calls for the scoped implementation and an observation of the option on the actual narrow surface. A diff alone does not fulfill the second part.
