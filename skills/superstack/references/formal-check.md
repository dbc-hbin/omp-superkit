# Formal checks and state diagrams

A request to draw a state transition calls for a diagram, not model checking. Show the important states, triggers, and guards using the requested format; use `skill://visualize` for a rendered local artifact when appropriate. Do not install a checker, use a remote renderer, or describe the diagram as verified. Use the procedure below only for an explicit request to check a property or to create or maintain a reusable formal verification method. A one-off property check does not authorize creating a skill.

## Check one property

1. Name the relevant code and state a concrete property in user terms, including the harm if it fails. Prefer a costly broken promise that examples seldom exercise, such as a timing-dependent state transition. Consult the existing contract, code, and callers to identify inputs, state owners, transitions, and error paths.
2. Use a locally available project-approved checker that fits the question: for example, a state-space tool for interleavings or a code-level verifier for an input property. Record its version, command, configurations, bounds, and assumptions. If it is unavailable or execution is not permitted, report what is missing and which claims remain unverified. Example runs or ordinary tests can give separate evidence, not a formal result.
3. Map model state, initial conditions, transitions, guards, and the property to actual files/functions and the relevant runtime contracts. Treat steps as atomic only when the implementation makes them indivisible; allow real interleavings at the other boundaries, including failures or retries that can change the result. State what the abstraction omits and why those omissions are valid for the claim. Do not exclude the scenario the property is meant to detect.
4. In authorized scratch space, run a deliberately broken variant that removes a relevant guarantee or reorders a step. Capture the actual counterexample and check that it breaks the intended property, not setup or a different rule. Run the unchanged model or code-level verification input with the same property and comparable bounds and preserve its actual result separately. Keep the deliberate break out of the product and the normal inputs. A negative check without a relevant counterexample, or a normal run stopped by an error, timeout, or exploration limit short of the stated scope, is not a verified pass.
5. Report the property, engine, command, input identity, bounds and assumptions, both outcomes, and what was not checked. Describe each counterexample as a sequence of implementation-level events. Say exactly what a normal pass covers: for example, all reachable states within the recorded model and bounds, not all production behavior. A model result applies to the implementation only to the extent the correspondence was established.

## Leave or maintain a reusable method

For explicit authoring, follow [the skill drafting contract](skill-authoring.md#draft-and-validate). Record the reproducible command, the property and code-to-model mapping, what to compare on code changes, the inputs or revision last checked for correspondence, and how to interpret a counterexample. Follow the written method for both runs before calling it verified. If the required tool, run permission, or authorized destination is unavailable, provide the plan or editable draft with the exact unverified parts.

For maintenance, record the existing check's result before editing. Find the last confirmed mapping and compare it to the current tree, including moved code, changed atomic boundaries, and new writers of the modeled state. A pass on the old description does not establish that it still models the product. Update the authorized verification artifacts to match observed implementation facts before using checker results to judge the updated model. Retain the promised property unless there is evidence of an intentional contract change within the approved scope; cite the evidence and report any changed assumptions or bounds. Never weaken a property just to pass.

Rerun the negative control and normal check. When an unmodified check reports a counterexample, trace each step against the current implementation. An impossible state or transition indicates model or harness drift: correct that mismatch and rerun. If the steps are feasible under the real contracts and still violate the promise, report a product defect with the trace and user impact. If feasibility cannot be established, report the unresolved step, not a confirmed bug or a pass. A stale model can previously have passed and then expose a real defect once corrected; distinguish the two results. Update the correspondence record only after establishing the mapping to the stated inputs, and report any failing property separately. Leave blocked mappings marked at their last confirmed inputs.

Edit only authorized skill, model, property, and harness files. Do not install Java, TLC, or other dependencies, use remote renders, change the product, or create a PR.
